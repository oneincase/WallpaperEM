# WebKit 4K 视频硬解 + 无缝循环 · 最小原型

一个零依赖的单页原型，用来**把「4K 视频在 WebKit 里为什么卡」拆成可单独测量的变量**。

它不解决别的问题，只回答三个：

1. 视频帧从解码器到屏幕走了哪条路，各条路代价差多少？
2. 四种循环方案，回绕时各卡多少毫秒？
3. 哪些看起来无害的 CSS/架构选择会**悄悄把硬件直通合成打掉**？

每个变量都做成了开关，指标全部现场量，不靠猜。

---

## 跑起来

```bash
# 1. 生成测试片（4K 无缝 / 4K 硬接缝 / 4K HEVC / 1080p 对照）
bash tools/make-clips.sh

# 2. 先验证素材本身真的无缝，否则后面量到的接缝没法归因
bash tools/verify-clips.sh

# 3. 起服务（必须走 http，见下方「为什么不能用 file://」）
node serve.mjs            # http://127.0.0.1:8787

# 4. 用 Safari 打开 http://127.0.0.1:8787 ，播放中另开一个终端跑：
bash tools/probe-decode.sh
```

想拿自己的片测，直接用面板上的**本地文件**选择框，不用改代码。

> **测的是 Safari，结论对 WKWebView 成立吗？**
> 是同一个 WebKit 引擎，视频解码/合成栈（VideoToolbox → IOSurface → CoreAnimation）完全共用。
> 差异只在宿主策略上（autoplay 限制、`desynchronized` 支持、窗口是否透明）。
> 所以**趋势和量级可以直接搬**，绝对值要回到 Tauri 里复测一次。

## 怎么判断「到底有没有硬解」

JS 侧查不到，`getVideoPlaybackQuality()` 只给你丢帧数，不告诉你走了哪条解码路径。只能从进程侧看，两个独立证据：

```bash
bash tools/probe-decode.sh
```

| 现象 | 结论 |
|---|---|
| `VTDecoderXPCService` 在跑且 CPU > 0 | 确实用了 VideoToolbox 硬件解码器 |
| 上一条成立 + 渲染进程 CPU < 30% | 硬解 **+ 直通合成**，这是理想态 |
| 上一条成立 + 渲染进程 CPU 100%+ | 硬解了，但像素被拉回 JS/WebGL —— 本原型的 `webgl` 路径 |
| 没有 `VTDecoderXPCService` 且 CPU 200%+ | 软解。检查编码格式（必须是 H.264 / HEVC） |

**关键认知：硬解成功 ≠ 流畅。** 硬解只保证解码不烧 CPU；像素之后还要跨进程搬一次才到屏幕，那一趟才是 4K 的真正瓶颈。

## 三种合成路径

面板中间那排按钮，切换的是**视频帧怎么到屏幕**。

| 路径 | 机制 | 4K/60fps 的像素搬运量 | 代价 |
|---|---|---|---|
| `direct` | video 元素直接上屏，VideoToolbox 解出的 `IOSurface` 零拷贝交给 CoreAnimation | **0**（合成器直取） | 几乎无。但要求祖先上不能有 `filter`/`opacity` 动画等离屏触发器 |
| `canvas2d` | 每帧 `drawImage(video)` | 全帧一遍 | 中等，WebKit 有加速路径 |
| `webgl` | 每帧 `texImage2D(video)` | 3840×2160×4 ≈ **33 MB/帧**，60fps ≈ **2 GB/s** | 最重。WebKit 必须把 GPU 侧的 `CVPixelBuffer` 同步拉回再当纹理上传 |

`webgl` 那一行就是「明明硬解了却还是掉帧」的根因。

> 这是算术，不是估计：4K RGBA 一帧 33MB 是定值，乘帧率就是每秒必须过的字节数。
> 具体掉多少帧取决于机型带宽，用页面上的**像素上传 ms/帧**和**丢帧率**实测。

## 四种循环方案

面板最上面那排按钮。

| 模式 | 做法 | 接缝来源 | 解码会话 |
|---|---|---|---|
| `loop` | 原生 `<video loop>` | 解码器到末尾要 flush + seek 回 0，这段没有新帧可上屏 | 1 |
| `seek` | 提前一帧手动 `currentTime = 0` | 比原生少一次 flush，但仍在一个会话里硬扛 | 1 |
| `pingpong` | 双实例：备胎停在第 0 帧待命，切换瞬间出帧 | **趋近 0**，seek 被藏进整个循环时长 | 2 |
| `crossfade` | 双实例 + 交叉淡化盖住接缝 | 0（淡化窗口内两层重叠） | 2 |

### 降级链：无缝做不到时怎么退

`pingpong` 是唯一能给出**真正零接缝**的方案，但它对时序敏感 —— 需要备胎精确 seek 到 0 且首帧已解码。如果实测下来它做不到（备胎没就绪、seek 太慢、双 4K 硬解会话吃不下），按这个顺序退：

```
pingpong  →  crossfade  →  crossfade + 加长淡化  →  单实例 loop
 真无缝      接缝被稀释       容忍更慢的备胎         接受接缝
 2 会话      2 会话           2 会话                1 会话
```

`crossfade` 不是「凑合」，它有两个 `pingpong` 没有的性质：

- **对时序不敏感。** 备胎迟几帧才出画面无所谓，那会儿它还是半透明。
- **接缝落在淡化中点。** 触发点提前**半个**淡化时长，接缝那一刻两层各 50%，跳变被稀释得最狠。

代价只发生在淡化窗口内（默认 200ms）。

### pingpong 为什么能无缝

不是「切得快」，而是**把慢动作挪到了看不见的地方**：

1. A 在播，B 已经 seek 到 0 并 `pause()` 在第一帧（首帧已解码进缓冲）
2. A 播到倒数第 `lead` 帧 → 立刻让 B `play()`，B 瞬间出帧
3. 同时把 A `pause()` 并 `currentTime = 0` —— 这次 seek 有**一整个循环时长**的余量去完成

代价是 2 个硬解会话。4K HEVC 下两个会话的显存开销要实测确认，短循环片（几秒）一般没问题。

`lead` 旋钮（提前多少帧切）值得调：太小会看到黑帧/旧帧，太大会吃掉下一轮的头部。默认 1 帧。

### crossfade 的真实账单

这里要说准，因为很容易误判成「淡入一定很贵」：

**对 video 元素本身做 `opacity` 过渡 → 是层混合，不是离屏渲染。**
video 已经是独立合成层（`translateZ(0)`），合成器直接在 GPU 上把两层 alpha 混合，不需要离屏 pass。
真实开销 = 2 个解码会话 + **淡化窗口内**约 2 倍的合成像素量。窗口之外只有一层参与合成。

**对祖先元素做 `opacity`/`filter` → 才会强制整棵子树离屏。** 那才是昂贵的，也是面板上「强制离屏」开关演示的东西。

两者差别很大，别混为一谈。面板 HUD 上的**「淡化状态」**会在淡化窗口内标记「◆ 双层合成」，对照这段窗口里合成帧率的变化，就能看出层混合在你这台机器上的真实开销。

如果实测下来淡化窗口内掉帧明显，先试**缩短淡化时长**（120~200ms 通常够盖住接缝），而不是直接放弃这个方案。

## 怎么读接缝指标

> **接缝 = 回绕那一帧的呈现间隔 − 正常帧间隔**

- 用 `requestVideoFrameCallback` 的 `expectedDisplayTime` 算间隔。它以 vsync 网格为基准，不会像 `performance.now()` 那样抖。
- 正常帧间隔不是硬编码 30fps，而是从 `mediaTime` 的相邻差取中位数现算，所以 24/25/60fps 素材都准。
- **0 = 无缝**；负数 = 比正常帧还早，等价于无缝。折算成「帧」更好判断：**超过 1 帧就肉眼可见**。

面板上的三档颜色：绿 = 无感，黄 = 临界，红 = 明显卡顿。

### 一定要用对照素材

`clips/loop-hardcut-4k.mp4` 是首尾不接的，用它能确认指标**确实在工作**（应该报出很大的接缝）。
如果拿无缝片测出来接缝是 0，但你分不清是指标坏了还是真无缝 —— 就先跑一遍硬接缝片。

`loop-seamless-4k.mp4` 是**匀速滚动的无缝纹理**：图案横向镜像拼成周期 3840 的纹理，6 秒恰好滚满一个周期。
末帧与首帧只差一个正常帧的位移，画面在回绕处完全连续 —— 剩下的任何卡顿都只能归因于解码/合成。

两片的滚动速度都是 640 px/s，只有时长不同（6s vs 4s），所以对比是公平的。

> **动手测之前先跑一次 `bash tools/verify-clips.sh`。**
> 它用 PSNR 验证素材本身是否真的无缝。这一步不能省：素材要是自己就顿一帧，
> 页面上量到的接缝就无法归因，整组实验作废。
> 判据是「回绕处的画面跳变量 ≈ 正常相邻帧的跳变量」，而不是「首帧 == 末帧」——
> 后者反而说明有重复帧。

## 会打掉直通合成的写法

面板上那个 **「强制离屏合成」** 开关就是在演示第一条：`#stage` 加一个 `filter: opacity(1)`（视觉上完全无变化），硬解没变，但帧率会掉。打开前后各看一次 CPU，差别很直观。

清单：

- 祖先元素上的 `filter` / `backdrop-filter` —— 最隐蔽的杀手，哪怕值是恒等变换
- 对 **video 的祖先** 做 `opacity` 动画（整棵子树被迫离屏）
- `mask` / `clip-path` / `mix-blend-mode` 动画
- 把视频画进 canvas / WebGL（就是本原型的后两条路径）
- 对 video 本身做连续 `transform` 缩放动画

注意和下面这条的区别：

- 对 **video 元素本身** 做 `opacity` 过渡 —— **不属于**这一类。它已经是独立合成层，
  层级的 alpha 混合在 GPU 上直接完成，不需要离屏。这正是 `crossfade` 模式可用的前提。
  差别在于「离屏」这个词：动的是**层的属性**还是**子树的内容**，成本差一个量级。

## 为什么必须走 http 而不是 `file://`

`serve.mjs` 特意实现了 **Range 请求（206 Partial Content）**，这不是可有可无的：

`pingpong` 模式的整个前提是「`currentTime = 0` 要快」。浏览器对视频 seek 走的是 HTTP Range。`file://` 下没有 Range，Safari 会把整个 4K 文件读进内存再 seek —— 测出来的 seek 耗时完全失真，内存也会被打满。

## 搬到 WallpaperEM 里要注意什么

这个原型的结论对 `renderer/src/main.ts` 直接适用：

1. **视频/GIF 类壁纸不该走 WebGL 纹理。** 现在所有类型统一进 `webwallgl`，视频帧逐帧 `texImage2D` —— 正是本原型的 `webgl` 路径，也正是代码注释里写的「WKWebView 下同步跨进程取像素，代价随像素数线性」。视频类应该退化成 `direct` 路径。

2. **代价是拿不到滤镜链。** 走 `direct` 就没法在 GPU 上对视频做后处理了。这需要在产品上做个取舍：要么 4K 视频不给滤镜，要么接受 `canvas2d`（比 webgl 轻，但仍非零）。

3. **`pingpong` 与现有「屏保/播放列表」逻辑要协调。** 这个原型只做单文件循环；`renderer` 里的轮播、属性订阅、系统音频注入都假设只有一个播放实例。双实例方案要额外定义「哪个实例响应暂停/seek 指令」。

4. **透明窗口是额外代价。** 壁纸窗口通常是透明的（`macos-private-api` + desktop-underlay），alpha 合成本身就比不透明窗口贵。原型的 `#stage` 是纯黑不透明，实际集成时需要单独测这一项。

5. **`videoTexScale` 那套画质档位可以省掉。** 它是为 `texImage2D` 的像素量做的妥协（按实测帧率压低上传分辨率）。走 `direct` 后上传量归零，这个旋钮就失去意义了。
